## Milestone 2, Stage 7 follow-up — closing self-reported coverage gaps (2026-10-29)

A self-audit of the Stage 7 integration suite (asked for explicitly, against the original item 3 checklist) found real gaps, including one actively misleading test title. Fixed, all against the real database:

- **The revoked-key 401 test's title claimed a case its body never built.** `policy-lifecycle.integration-spec.ts` had one test titled "...for a missing, malformed, revoked, and wrong-scope key" whose body only ever constructed 3 of those 4. Split into two tests: the original (renamed to drop "revoked") and a new one that creates a key, calls the REAL `ApiKeyRepository.revoke(id)` via the app's own DI container, confirms the key worked *before* revocation (so the 401 after can't be mistaken for some other failure), and asserts the post-revocation response is byte-identical (`toEqual`) to a missing-key 401.
- **Adversarial tenant isolation, with a positive control** (`tenant-isolation-adversarial.integration-spec.ts`, new file): the original two-tenant test never proved isolation was load-bearing - tenant B's chunk might never have outranked tenant A's own chunk anyway. This one uploads content to tenant B that is the query text verbatim (cosine ≈ 1.0 under the deterministic hashing embedder) and unrelated filler to tenant A, then runs a RAW, UNFILTERED `$vectorSearch` (no `tenantId`/`active` filter at all - built only in this test file, explicitly never in production code) to prove B's chunk really is the single best match across every tenant. Only then does it check tenant A's real, filtered `retrieve()` - zero of B's results - and tenant B's own `retrieve()` - does return it, ruling out an always-empty-results bug passing as isolation.
- **Mid-commit rollback against the real database** (`commit-rollback.integration-spec.ts`, new file): resolves the REAL `TransactionRunner` and REAL `PolicyChunkRepository` from the app's DI container (not the fakes the existing unit test and `check-transactions.ts` script use), runs `insertMany()` inside a real session, then throws before the callback returns. Asserts `countForTenant() === 0` afterward - MongoDB's own atomicity, not `PolicyIngestionService`'s fallback cleanup delete (that fallback exists specifically because in-memory fakes have no real rollback of their own; this test bypasses it entirely to prove the real guarantee it's a safety net for).
- **Deactivation isolated from deletion** (`deactivation.integration-spec.ts`, new file): calls `chunkRepository.deactivateForDocument()` directly, never `deleteForDocument()`, then calls `retrieve()` immediately with **no polling** - the specific case the earlier deactivation-leak fix was for. Also asserts the chunk is still physically present (`countForTenant() > 0`) afterward, so the zero-results assertion can't be mistaken for the chunk simply not existing.
- **Exact vs. approximate agreement** (`exact-vs-approximate.integration-spec.ts`, new file): a 6-chunk document, `retrieve({ exact: true })` vs `retrieve({ exact: false })`, asserting the same set of `chunkKey`s comes back from both, and every score from both calls is within `[0, 1]`.
- **Quota and concurrency** (`quota-and-concurrency.integration-spec.ts`, new file): `DOCUMENT_QUOTA_EXCEEDED` and `CHUNK_QUOTA_EXCEEDED` against a dedicated app instance with `INGESTION_MAX_DOCUMENTS_PER_TENANT`/`INGESTION_MAX_CHUNKS_PER_TENANT` forced small via env, so the quota is reachable without uploading dozens of real documents. `TENANT_BUSY` uses a `GatedLlmProvider` whose `embed()` blocks on a manually-released gate instead of a sleep - deterministic, because `TenantIngestionLock.tryAcquire()` runs synchronously before any `await` in `ingest()`, so the lock is guaranteed held by the time the second request fires.
- **Repo-wide title-vs-body audit**: ~422 `it(...)` titles checked (compound-claim titles read in full; recently-touched files prioritized). One more real gap found beyond the ones above: `policy-retrieval.service.spec.ts`'s logging test claimed to verify 5 specific fields were logged but only ever checked 2 substrings. Fixed to parse the actual JSON log line and assert each claimed field's presence and type, plus that no extra field snuck in. No other title/body mismatches found; a few short titles (e.g. "revoked key", "caps length") rely on their enclosing `describe` block for context but aren't misleading.

**Still intentionally not integration-tested** (a decision, not an oversight - see the main Stage 7 entry below): transaction-failure-mid-commit through `PolicyIngestionService`'s own HTTP path specifically (the rollback mechanism itself is now proven directly, above, against the real database - what's not re-proven is the controller/service's own catch-and-cleanup wrapper around it, which is already unit-tested with a throwing fake).

## Milestone 2, Stage 7 — integration tests against a real database, and CI (2026-10-29)

**What was built**: `apps/api/test/integration/` - a harness that boots the REAL `AppModule` (real Mongoose repositories, real `TransactionRunner`, real `ApiKeyGuard`) with only `LLM_PROVIDER` overridden by `FakeLlmProvider`, against one fixed test database gated by its own env var, `MONGODB_TEST_URI` (never `MONGODB_URI` - that stays whatever a developer's own `pnpm dev` is using). Two spec files: `policy-lifecycle.integration-spec.ts` (full upload -> poll-until-searchable -> retrieve -> delete, duplicate -> 409, bad extension -> 422, the four 401 variants, two-tenant isolation) and `embedding-failure.integration-spec.ts` (a real mid-pipeline embedding failure, via a provider that fails on its second call against a document forced into two batches, proving zero committed chunks and a `failed` document - through the real commit path, not a fake transaction runner).

**Why a separate vitest config, not one more file in the existing suite**: `vitest.integration.config.mts` (`pnpm run test:integration`) is entirely separate from `vitest.config.mts` (`pnpm run test`) so the fast, database-free unit/e2e job is never slowed down or made flaky by network-dependent tests. Every integration spec does `describe.skipIf(!integrationTestsEnabled())`, so the suite reports as cleanly **skipped** (not failed, not silently absent, exit code 0 - confirmed by running it locally with no `MONGODB_TEST_URI` set) when there's no test database configured, which is the normal state for a local run without a real cluster.

**Two database guards, mirror images of each other**: `assertNotTestDatabase` (existing, Stage 2/6) refuses a *script* that would churn index/data state unless the database does NOT look like the shared test one. The new `assertIsTestDatabase` (`database-name.ts`) refuses the *integration suite* unless the database DOES look like it - a misconfigured `MONGODB_TEST_URI` must fail loudly, never quietly run against a real tenant's data.

**Index setup is NOT reimplemented for tests**: `test/integration/ensure-test-indexes.ts` calls the exact same `ensureIndexes()` exported by `src/scripts/db-ensure-indexes.ts` that a developer runs manually - one function, one mental model, proven to behave identically for a developer's own run and for the suite's own `beforeAll`.

**Tenant cleanup**: `tenant-fixture.ts` creates a tenant with a random id (`it-<uuid>`) and tears it down by `tenantId` across every collection at the end of each spec file's `afterAll` - never `dropDatabase`, because the test database is shared by the whole suite (and, in the real-cluster local path below, by a developer's actual Atlas project).

### Atlas Local research (verified against current docs and Docker Hub, not assumed)

- **Image**: `mongodb/mongodb-atlas-local`. Pinned to a specific build in CI, not `latest`: `8.0.20-20261027T181252Z` (the newest available at research time, 2026-10-29; multi-arch amd64+arm64). Confirmed the repo also publishes rolling `latest`/`preview`/`8.0`/`7.0` tags, all deliberately avoided for CI reproducibility.
- **Health check**: built into the image itself (a real Docker `HEALTHCHECK`) - no custom `--health-cmd` needed. GitHub Actions service-container health gating only works automatically for images that define their own `HEALTHCHECK`; this one does, confirmed via GitHub's own Actions docs, so `docker inspect --format '{{.State.Health.Status}}'` polling is accurate whether the container is started via `services:` or a plain `docker run` (CI uses the latter, for direct log access on failure).
- **Connection string**: `mongodb://localhost:27017/?directConnection=true` - required because the image runs as a single-node replica set internally, not a standalone `mongod`.
- **Transactions**: supported. The single-node-replica-set design is specifically what makes multi-document transactions work locally at all (MongoDB has required a replica set for transactions since v4) - the same requirement real Atlas has.
- **Vector search**: supported (`$vectorSearch` via Atlas Search), confirmed on the image's own Docker Hub description. The `preview` tag additionally ships an experimental auto-embedding search feature this project doesn't use.

All five of the above were, at the time this subsection was first written, confirmed only from documentation - **the first real CI run (2026-10-29, see below) has since confirmed every one of them empirically**, against this project's own pinned image, not just read about. The "not yet empirically measured" caveat this subsection used to carry is gone - see the results section below for the actual numbers.

### First real CI run against Atlas Local (2026-10-29) — what it proved, what it broke, and what that fixed

The `integration-tests` job ran for the first time ever against a live `mongodb-atlas-local:8.0.20-20261027T181252Z` container. 3 of 7 spec files passed outright; 4 failed. The failures were all real bugs in the test suite itself, not flakiness or a problem with Atlas Local - diagnosed by reading the actual chunker/concurrency code, not assumed, then fixed (none of the fixes below have been re-verified by a second real CI run yet - that's the next thing to confirm).

**What passed, and what that proves for real, against this project's own pinned image**:
- `commit-rollback.integration-spec.ts` passed - **multi-document transactions work on Atlas Local**: a real `session.withTransaction()` callback that calls the real `insertMany()` and then throws before returning left `countForTenant() === 0` afterward, exactly as it does on real Atlas M0.
- `policy-lifecycle.integration-spec.ts` and `deactivation.integration-spec.ts` passed - **`$vectorSearch` and `createSearchIndex` both work for real**: documents were uploaded, embedded, searched for, and found; deactivation was observed to take effect immediately against a live re-check, exactly as designed for real Atlas's eventual consistency.
- The `ensure-test-indexes` log from this run recorded the index going from `PENDING` to queryable in **10 seconds** on Atlas Local (`Index "policy_chunk_vector_index" is queryable after 10s`) - in the same range as the 2.1s-10.3s insert-to-searchable lag this project separately measured on real Atlas M0 (see the Stage 6 follow-up entry above), though this is one data point, not a guarantee either way.

**What failed, and the real bug each one found**:
1. **`tenant-isolation-adversarial.integration-spec.ts`**: `expected 0.8535... to be greater than 0.99`. Not a product bug - the test's own assumption was wrong. `buildEmbeddingText()` (markdown-chunker.ts) prepends a chunk's `headingPath` to its body before embedding, so a chunk whose body is the query text verbatim still doesn't embed as pure query text. Fixed (per explicit follow-up request) by replacing the absolute threshold with a relative one: the raw unfiltered top hit's score must exceed tenant A's own best real score, not clear some arbitrary number tied to the fake embedder's internals.
2. **`embedding-failure.integration-spec.ts`** (expected 502, got 201) and **`exact-vs-approximate.integration-spec.ts`** (expected chunkCount >= 6, got 1): both test fixtures assumed one heading = one chunk. `mergeTinySections()` (heading-sections.ts) merges same-parent sibling sections under `minMergeTokens` (100 tokens, ~400 characters) - every fixture section in both files was a few dozen characters, so everything merged into a single chunk regardless of heading count. Fixed by rewriting the fixtures (and the latent identical bug in `quota-and-concurrency`'s chunk-quota test, which hadn't run yet when the job failed but had the same flaw) with section bodies well over 400 characters each.
3. **`quota-and-concurrency.integration-spec.ts`**: `MongoServerError: duplicate index names for the same collection`, then a cascading `TypeError` (`app` was never assigned) and two timeouts (150s hook, 90s test) in the same file. Real concurrency bug: `ensureTestIndexes()`'s "only run once" guard was a module-level variable, but vitest runs every spec file in its **own worker process** by default - the guard only protected one file at a time. Two files raced to create the same not-yet-existing search index simultaneously; MongoDB's real, non-idempotent `createSearchIndex` has no way to resolve that race gracefully. Fixed by moving index creation into vitest's `globalSetup` (`test/integration/global-setup.ts`), which runs exactly once, in the root process, before any worker spawns - structurally race-free, not just guarded. The per-file `beforeAll` calls to `ensureTestIndexes()` were removed from all 7 spec files as a result.
4. The TENANT_BUSY test's 90s timeout had a second, independent cause even setting aside the index race: its synchronization (`await new Promise(resolve => setImmediate(resolve))`, assuming one microtask tick was enough for request 1 to reach the lock before request 2 fired) was a timing guess, not a guarantee. Fixed with an explicit signal instead: `GatedLlmProvider` now resolves a promise the instant `embed()` is actually entered, and `release()` is called in a `finally` block so a failed assertion can never leave the gate open and hang the file's own `afterAll` again.

**Lessons for this test harness specifically, going forward**:
- Vitest spec files are separate OS processes by default (`isolate: true`, the default and now pinned explicitly in `vitest.integration.config.mts`) - any setup that must happen exactly once across the whole suite belongs in `globalSetup`/`globalTeardown`, never in a per-file `beforeAll`, no matter how good that file's own "already done" guard looks on paper.
- `isolate: true` is load-bearing for a second reason too, beyond the index race: several specs temporarily mutate `process.env.INGESTION_*` for the duration of one file's tests. With `isolate: false` (vitest's own suggested speed-up), a shared worker process would leak one file's env mutations into another file scheduled onto the same worker.
- Any fixture meant to produce more than one chunk from a markdown document must give each section a body comfortably over `minMergeTokens` (100 tokens / ~400 characters) - the chunker's tiny-section merge is real, documented, correct behavior, not a bug to work around.
- A score-based assertion against a real embedding call should compare relatively (this run's result vs. another real result from the same run), never hardcode an absolute number derived from reasoning about an embedder's internals - that reasoning can be wrong in ways only a real run exposes.

## Milestone 2, Stage 6 follow-up — a real deactivation leak, diagnosed and fixed (2026-10-29)

**The report**: the retrieval smoke test (Stage 6, item 11) failed its "inactive chunks are never returned" check on a real run - after deactivating a tenant's chunk, `retrieve()` still returned it. Diagnosed per the explicit instruction to not assume the cause, by extending the smoke script to inspect the raw collection state and the raw `$vectorSearch` output directly, rather than only the service's own return value.

**Diagnosis, with real numbers from this project's own Atlas M0 cluster**:
- The deactivation write itself was correct and immediate: `updateMany` reported `matched: 1, modified: 1`, and a direct `findOne` read of the collection (bypassing the index entirely) confirmed `active: false` right away. **Not a bug in `deactivateForDocument()`.**
- A raw `$vectorSearch` call issued immediately after the write still returned the chunk as a candidate - the index's own copy of `active`, which the pre-filter narrows candidates against, had not caught up yet. This is Atlas Vector Search's documented eventual consistency (already noted in this file for *new* chunks becoming searchable after insert) applying the same way to a *field update* on an existing, already-indexed chunk - a case this project hadn't previously tested.
- **Measured lag, across runs**: insert-to-searchable lag (a freshly-inserted chunk becoming visible to `$vectorSearch` at all) was measured at **10.3s** on one run and **2.1s** on another - both from the same smoke script against the same cluster, run at different times. Field-update lag (an already-indexed chunk's `active: false` becoming visible to the pre-filter) was much shorter: about **0.1s**. All of these are **observations across a handful of runs, not a guarantee** - Atlas gives no documented upper bound for either kind of lag, which is exactly why the fix below never depends on timing, and why integration tests (Stage 7) must poll for up to 60 seconds with an informative failure message rather than asserting on the first try.

**The key experiment, which is what makes the fix valid**: does `$vectorSearch`'s own `$project` output for a field reflect the document's *current* collection value, even while the index still treats the document as a stale candidate? Tested directly: immediately after deactivating, a raw `vectorSearch()` call still surfaced the chunk, but its projected `active` field read `false` - matching the live collection value exactly. **Confirmed: `$project`'s output is live, even when the pre-filter's candidate selection is stale.** This is the fact that makes a post-search field check valid instead of just another guess - the alternative design item 2 raised (a follow-up per-chunk lookup by id) was not needed.

**The fix**: `buildVectorSearchPipeline()` now also projects `active` (it already projected `tenantId`). `PolicyRetrievalService.retrieve()` re-checks both fields on every result after the search and drops (logging only a count, never content) anything whose live `tenantId`/`active` no longer match what's required - `DEFENSE_IN_DEPTH_CROSS_TENANT_RESULT` and `DEFENSE_IN_DEPTH_INACTIVE_RESULT`. The existing doc comments claiming the pre-filter alone made cross-tenant/inactive results "impossible" were corrected - that was an overclaim even before this bug was found; the pre-filter is a real optimization (it narrows the HNSW traversal), not a standalone guarantee.

**Deletion, checked the same way**: deleting a chunk and immediately calling `retrieve()` returned no leaked result in this run - a deleted document has nothing left for `$project` to join against, so there's no live field to misreport. Not proven absent in every possible timing, but no reproduction was found, and the general rule below covers it regardless.

**The governing rule, going forward**: *index results are candidates, the collection is the source of truth.* Nothing downstream of `$vectorSearch` may treat its output as already correct - every field that matters for a safety decision (tenant, active state) must be read from the search result's own `$project`ed, live values and re-checked, never assumed from the fact that the document matched at all.

**The 0.5 score is independent evidence for the normalization formula**: querying tenant A with tenant B's completely unrelated text (and vice versa) scored exactly **0.5** in the real run. Under `(1 + cosine) / 2`, a score of 0.5 means cosine ≈ 0 (orthogonal) - exactly what two documents sharing no words should produce under a hash-based bag-of-words embedder. This is a second, independent empirical data point for the formula already documented in the Stage 6 entry below (which could only be corroborated from secondary sources, not fetched directly from MongoDB's own page at the time).

**A second, related gap - crowding, not just leaking**: dropping stale/inactive candidates after the search closes the correctness gap, but not a quality one. `$vectorSearch`'s `limit` is a fixed ceiling on how many candidates come back at all; while the index is stale, candidates that will turn out to be dropped can still occupy slots up to that ceiling, leaving fewer than `topK` genuinely valid results in the batch to choose from - a valid chunk can be crowded out entirely, not just re-ranked. Fixed by over-fetching: `PolicyRetrievalService.retrieve()` now asks `vectorSearch()` for `topK * 2` candidates, runs the existing drop logic, and only then trims to `topK`. 2x is an arbitrary but cheap multiplier - `numCandidates` is already separately capped at `ATLAS_MAX_NUM_CANDIDATES` inside `buildVectorSearchPipeline()`, so doubling `limit` does not risk exceeding Atlas's own ceiling. Proven with a fake repository returning two stale/inactive results ranked ahead of two valid ones (`topK: 2`): the service is asserted to request `limit: 4` and to return exactly the two valid chunks.

**Caveat, stated explicitly**: every score in this smoke test (0.835, 0.854, 0.5, ...) comes from `FakeLlmProvider`'s deterministic hashing embedder, used specifically so the test spends no Gemini quota. These numbers say nothing about what real Gemini embeddings would score for real policy text - they're useful only for confirming the *scoring formula* (additive/multiplicative structure, the 0.5-at-orthogonal property), never for judging real relevance or picking a future threshold. That is still deferred to Stage 8, against real embeddings of the sample policy fixture.

## Milestone 2, Stage 6 — Retrieval

**What was built**: `apps/api/src/retrieval/` - `PolicyRetrievalService.retrieve(tenantId, query, options)`, a service (not an HTTP endpoint - the Milestone 3 agent will call it directly, the same way `PROJECT.md`'s single ticket flow describes the Retriever step). Validates the query and `topK`, embeds the query with `taskType: RETRIEVAL_QUERY` through the existing Stage 3 provider (which already caches - no new caching code needed here), calls the repository's `vectorSearch` with a mandatory `tenantId` + `active:true` pre-filter, re-checks every result's tenant after the fact (defense in depth), skips any result embedded with a stale model/dimension, and logs only shape (tenantId, query length, result count, top score, duration) - never query or chunk text.

**`numCandidates` has a real, documented maximum**: confirmed directly against current MongoDB docs (not assumed) - `numCandidates` "must be less than or equal to (<=) 10000". `buildVectorSearchPipeline()` (a pure function, extracted specifically so a test can inspect the generated pipeline directly rather than mocking Mongoose) now caps the 20x-limit default at that maximum.

**Score semantics, verified as far as possible**: for a cosine-similarity Atlas Vector Search index, `vectorSearchScore` is normalized to `[0, 1]` via `(1 + cosine) / 2`, not the raw cosine value - cross-checked across several independent sources (MongoDB's own `$similarityCosine` operator docs state this formula explicitly for its own normalized mode, and multiple vector-search guides and the project's own prior research corroborate the same formula specifically for `$vectorSearch`'s score). The one gap, stated honestly rather than glossed over: the primary `$vectorSearch` stage reference page itself returned a content-too-large error on every direct fetch attempt during this verification pass, so the formula is corroborated, not confirmed from that single canonical source. No relevance threshold is applied on top of this score yet - deferred to Stage 8, which will look at the real score distribution against the sample policy fixture before picking one, rather than guessing a threshold now and tuning it blind.

**Two real bugs, both caught by writing the actual test rather than assuming the design was right**:
1. `chunkKey` was never a persisted field (Stage 5's `NewPolicyChunk` never carried it into the database) - the retrieval result's `chunkKey` is computed at query time instead, from the two fields that ARE persisted and are genuinely stable: `${documentId}-${position}`.
2. `GUARDS_METADATA` imported from `'@nestjs/common'`'s main index is `undefined` at runtime in this project's swc/vitest setup, despite the package's own `.d.ts` declaring it there - confirmed directly by a forced-failure scratch test. `PATH_METADATA`/`METHOD_METADATA` already worked correctly from the `'@nestjs/common/constants'` subpath (allowed by that package's own `"./*": "./*.js"` exports map); `GUARDS_METADATA` needed the same subpath import, not the main one. Found while building the route-auth-coverage test (item 7) - a route-level NestJS metadata check is exactly the kind of thing that silently "passes" for the wrong reason (every route looks unguarded, including the real ones) if this goes unnoticed, which is why that test file also includes two deliberately-misconfigured-controller cases proving the check actually flags a real violation, not just a theoretical one.

**Interview Q&A**: *"How do you know retrieval can't leak another tenant's data, even if there's a bug somewhere?"* - Two independent layers, not one: the `tenantId` filter is applied INSIDE the `$vectorSearch` stage itself (a pre-filter that narrows the HNSW graph traversal before ranking happens, confirmed by a test that reads the actual generated pipeline, not just the intent), and every result is checked again in the service after the search returns, with a mismatch dropped and logged rather than trusted. The second layer is deliberately redundant - it exists specifically so a future regression in the first layer fails loudly (a logged, countable event) instead of leaking data silently.

## Milestone 2, Stage 5 follow-up — three real bugs, found only by running the real server (2026-10-28)

Everything in the Stage 5 entry below passed its full test suite (allowBuilds experiment, stale-pending hardening, module-wiring unit tests) before any of this - none of it caught these three, because none of it actually ran the real app against a real database and a real Gemini key. All three were found in a single manual test pass (`pnpm run build && pnpm run start`, then the upload/list/duplicate/delete sequence from this project's own manual-testing instructions) and are a good argument for why "all tests pass" and "it actually works" are different claims.

**1. IngestionModule never imported DatabaseModule.** `PoliciesController`/`PolicyIngestionService`'s `@Optional()` repository tokens silently resolved to `undefined` - every request returned `503 NOT_CONFIGURED`, indistinguishable from `MONGODB_URI` genuinely being unset. Root cause: NestJS module providers aren't visible across sibling imports just because they share a parent - `AppModule` importing both `DatabaseModule` and `IngestionModule` does not make `DatabaseModule`'s exports visible inside `IngestionModule`; each module that uses a token must import the module that provides it. `AuthModule` already did this correctly (self-contained, conditional on `MONGODB_URI`) - `IngestionModule` just never got the same treatment. The controller-level tests (`policies.controller.spec.ts`) never caught this because they hand-assemble providers directly in a flat `Test.createTestingModule`, bypassing the real import graph entirely. Fixed by giving `IngestionModule` the same self-contained conditional import, and added `ingestion.module.spec.ts`, which inspects `@Module` metadata directly (via `Reflect.getMetadata('imports', ...)`) rather than booting a real app - this is now the project's go-to pattern for catching this bug class without a real database.

**2. The transaction session came from the wrong Mongoose connection.** Even after fix 1, every commit failed with `Connection operation buffering timed out after 10000ms`. Root cause: `@nestjs/mongoose`'s `MongooseModule.forRoot()` calls `mongoose.createConnection(uri, options)` internally (confirmed by reading its source) - an isolated `Connection` instance, never the bare default `mongoose.connection`. `TransactionRunner` was calling the global `mongoose.startSession()` (via `import mongoose from 'mongoose'`), which started a session on a connection that was never actually connected to anything. Every operation passed that session (`insertMany`, `markReady`) buffered against the real, working connection's models while waiting on an unrelated disconnected one, until Mongoose's own 10s buffering timeout gave up. This is also why the earlier `check-transactions.ts` probe script's success was real but non-transferable: that script calls `mongoose.connect()` directly, so there was only ever one connection in play - it never exercised the two-connection mismatch this app's actual module wiring has. Fixed with `@InjectConnection()`, getting the session from the same `Connection` the repositories' models are registered on.

**3. The chunker can legitimately produce an empty-text chunk, and the schema rejects it.** A heading with no body of its own before its first subheading (`## Refund Policy` directly followed by `### Standard Refund Window`, nothing between them - exactly the shape of the real `sample-policy.md` fixture) has no same-parent sibling to merge into (Stage 4's own, deliberate, documented behavior), so it's kept as its own section - sometimes genuinely empty, sometimes containing nothing but the literal absorbed heading markup from a backward merge (e.g. `"# A\n"`). `PolicyChunk.text` is `required: true`, and Mongoose rejects an empty string for `required` String paths (same category of gotcha the `embedding` array and `headingPath` fields already hit). Fixed by filtering `chunks.text.trim().length === 0` out of the chunk list in `PolicyIngestionService`, after chunking and before quota checks/embedding - nothing is lost, since a heading with no body of its own still appears in every one of its real subsections' `headingPath`.

**What this changes about the commit-failure path**: the `catch` block around the transaction previously swallowed the real error with zero logging (`catch {}`, no variable). Bug 2 was effectively undiagnosable from server logs alone until that was fixed first - now logged as `{event: "policy_commit_failed", tenantId, documentId, error: message}` (an infrastructure/driver error message, never document content, so safe to log under the same rule as everything else in this pipeline).

**Interview Q&A**: *"Your test suite was fully green - how did you still find three bugs?"* - Because the tests validated units and a hand-wired HTTP layer, never the real dependency-injection graph connected to a real database. The fix wasn't "write a test that would have caught this in hindsight" for all three (bug 2 specifically needs a real multi-connection Mongoose+Nest setup that's impractical to fake convincingly) - it was recognizing which failure mode each bug represents (wrong module graph, wrong connection object, a pure function's edge case meeting a database constraint) and fixing the right layer for each, then adding the one regression test (module metadata inspection) that's actually cheap and real.

## Milestone 2, Stage 5 — Ingestion pipeline and policy endpoints

**Transaction decision (2026-10-28)**: multi-document, multi-collection MongoDB transactions were verified empirically against the project's real Atlas M0 cluster, via a probe script (`apps/api/src/scripts/check-transactions.ts`, kept as a permanent manual tool - reusable if the cluster is ever migrated or the question needs re-checking) that inserted one document and updated another inside a single `session.withTransaction()` call, using a scratch collection it drops afterward either way. Result, reported directly by the developer running it:

```
Target database: "support_Pilot"
Scratch collection: "_transaction_probe" (dropped at the end regardless of outcome)
Transaction committed without error.
After commit - seed.value updated to 2: true
After commit - second document visible: true
RESULT: transactions work on this cluster.
```

**Decision made from that result**: the commit step embeds every chunk in memory first, then performs ONE `session.withTransaction()` call that both inserts every chunk (`active: true` directly - no separate "insert inactive, then activate" phase) and marks the parent document `ready`. This replaced an earlier two-phase design (insert inactive, activate, mark ready) that existed only as a fallback for a cluster where transactions might not work. Since M0 is a 3-node replica set and transactions are confirmed working, that fallback was never built as a real code path - RULES.md's "no dead code" argues against shipping an untested branch "just in case." The `active` field itself is kept anyway, as the safeguard for DELETE's ordering (deactivate, delete chunks, delete the document) and as the Atlas Vector Search index's pre-filter field.

`session.withTransaction()` (not manual `startTransaction`/`commitTransaction`) is used specifically because it's MongoDB's own documented pattern for retrying the whole callback automatically on a `TransientTransactionError`, and retrying just the commit on an `UnknownTransactionCommitResult` - this is what "rely on the driver's transient-error retry" means here, not a hand-rolled retry loop.

**Defense in depth, not solely reliant on Mongo's own rollback**: if the transaction callback throws for any reason, the calling code explicitly deletes any chunks for that document and marks it `failed` - this is a safety net that's a harmless no-op against the real transactional backend (which already rolled back automatically) but is what actually makes "zero chunks on failure" true against the in-memory fakes used in unit tests, which have no real transactional rollback of their own. A dedicated test (`policy-ingestion.service.spec.ts`: "a failure inside the commit step leaves zero chunks and a failed document") injects a repository that throws partway through the commit and asserts exactly that.

**Atlas Vector Search is eventually consistent**: a chunk that was just committed (even inside a successful transaction) can take a few seconds before `$vectorSearch` actually returns it - the vector index update happens asynchronously, outside the transaction. Any future integration test that uploads a document and then immediately searches for it must poll for the expected result with a timeout, never assert it on the very next call. No such test exists yet (retrieval is a later stage), but this is the governing rule for when one is written.

**A real architectural fix, not just new code**: requirement 1 ("if MONGODB_URI or GEMINI_API_KEY isn't configured, return a clear 503... and the app must still boot") couldn't be satisfied by the existing pattern of conditionally importing `DatabaseModule` and `AuthModule` together - that would leave `/v1/policies` returning a bare 404 (route never registered) instead of a 503 when there's no database at all. Fixed by making `AuthModule` self-sufficient: it now conditionally imports `DatabaseModule` *internally* (mirroring the same env-check that used to live only in `app.module.ts`), and `ApiKeyGuard`'s repository dependency is `@Optional()` - when absent, the guard throws a 503 itself (never a silent auth bypass, never a crash). `IngestionModule` is now always imported, same as `AuthModule`, matching `LlmModule`'s existing "always boots, fails per-call instead" philosophy from Stage 3.

**Real bugs found by writing the tests, not just by reasoning about the code**:
- `import { Request } from 'express'` as a bare (non-`type`) import compiles fine but isn't actually resolvable at runtime from `apps/api`'s own `node_modules` (`express` is only present transitively, via `@nestjs/platform-express`) - it only "worked" because the bundler happened to elide an import used solely in type position. Multer has the exact same problem, one level further: `memoryStorage()` is a genuine runtime call, which can't be elided - solved by writing a tiny inline storage engine (two callback-based methods, matching multer's own `StorageEngine` contract exactly) instead of importing anything from the `multer` package at all.
- `@RequireScope('secret')` applied at the *controller class* level (rather than per-method, as Stage 2's own tests only ever exercised) was silently never checked - `ApiKeyGuard` read scope metadata with `reflector.get(key, context.getHandler())`, which only looks at the method, never the class. Fixed with `getAllAndOverride(key, [context.getHandler(), context.getClass()])`, the standard NestJS pattern for "method overrides class, but either is honored."
- `@nestjs/platform-express`'s `FileInterceptor` already converts multer's raw errors into standard Nest exceptions itself (`LIMIT_FILE_SIZE` -> `PayloadTooLargeException`, every other limit -> `BadRequestException`) - confirmed by reading its source. A filter written to catch a raw `MulterError` (via a `.name === 'MulterError'` shape check) never fires, because that error never reaches any filter in that form. Fixed by catching the two actual exception types Nest itself throws.
- Mongoose's `required: true` on a `String` path rejects an empty string (`SchemaString._checkRequired = v => ... && v.length`, confirmed by reading `mongoose/lib/schema/string.js`) - the same category of gotcha Stage 1 found for an empty `[Number]` array. `headingPath` (which is legitimately `''` for content with no heading) needed `default: ''` *without* `required: true`.

**Interview Q&A**: *"How did you verify the transaction design would actually work, rather than just assuming MongoDB Atlas supports it?"* - By writing a disposable script that ran a real multi-document transaction against the developer's own Atlas M0 cluster and reporting the literal output, rather than relying on "M0 is a replica set, so it should work." The result is recorded here with its date, and the commit design (one transaction, no two-phase fallback) was decided only after seeing it succeed - the alternative, untested fallback path was deliberately never built.

## Milestone 2, Stage 4 — Markdown chunker: a pure function, no DB, no LLM

**What was built**: `apps/api/src/ingestion/chunking/` - `chunkMarkdown(text, options)`, a pure, deterministic function with no I/O. Normalizes CRLF, strips front matter, splits on ATX headings (`#`-`######`, ignoring `#` lines inside fenced code blocks), merges tiny sibling sections under the same parent, and packs oversized sections into ~300-500-token chunks with ~50-token overlap via a paragraph→sentence→hard-split fallback that never splits a UTF-16 surrogate pair and never splits a fenced code block or table row unless that block alone exceeds the limit.

**Key design decision - offsets ARE the text, not alongside it**: every `Chunk.text` is defined to always equal exactly `content.slice(chunk.startOffset, chunk.endOffset)` of the normalized, front-matter-stripped content - never a separately-trimmed or reconstructed string. This was enforced by construction (trimming adjusts the *offsets*, never re-slices a second copy of the text), which is what makes the "offsets slice back to the original text" test requirement trivially true for every chunk, including merged and split ones, rather than needing a special case.

**Merge asymmetry, found and documented rather than "fixed" into false symmetry**: a tiny section merges into a sibling under the same parent (never into its own parent - a heading and its child aren't siblings of each other). Backward merge (absorb into the preceding sibling) naturally includes the absorbed section's own heading line as inline text, because that heading line sits in the gap the offset range already has to cross. Forward merge (absorb into the following sibling) does not reach back far enough to include it, since the heading line sits in the gap *before* the tiny section's own start, which forward merge never needs to cross. Both are offset-correct; the difference is purely cosmetic (whether a stray `## Heading` line ends up inline in the merged body text). An initial version of this doc comment claimed full symmetry before a real test proved otherwise - fixed by writing out the actual gap mechanics rather than assuming both directions behaved the same.

**Overlap is "no gaps", not "always extra text"**: consecutive chunks produced from the same section are allowed to have overlapping offset ranges (`next.start < prev.end`) by construction, with no text duplicated in memory - "overlap" here means two chunks' ranges genuinely intersect. The one place this is NOT guaranteed is the last chunk at the tail of a section, which can be smaller than the configured overlap window itself (there's nothing further back to overlap into without exceeding the section's own start) - the tests assert "no coverage gaps" (`<=`) as the hard invariant and "overlap occurs at least once" as the softer one, rather than asserting strict overlap on every single pair.

**Interview Q&A**: *"How do you guarantee a chunk's offsets are trustworthy enough to reconstruct the original text?"* - By making the offsets the single source of truth for the text instead of two parallel representations: trimming, merging, and splitting all operate on the numeric start/end range, and `chunk.text` is always a direct slice of the same normalized content string using that exact range. There's no second code path that could independently drift from the real text, so the invariant holds by construction, not by a separate check.

## Milestone 2, Stage 3 — LLM provider: Gemini embeddings, verified against the real SDK

**What was built**: `apps/api/src/llm/` — the `LlmProvider` interface (`embed()` only; `generate()` deferred to Milestone 3), `GeminiLlmProvider` (the real implementation), `ThrottledClient` (rate limit + bounded concurrency + backoff), `EmbeddingLruCache` (bounded in-process LRU), a `FakeLlmProvider` test double (feature-hashing bag-of-words), and a manual `embedding-smoke-test` script. `EMBEDDING_MODEL`/`EMBEDDING_DIMENSION` moved to `@supportpilot/shared` so the LLM provider and the Mongoose vector index definition can never silently diverge — enforced by a test.

**Verified directly against the installed `@google/genai@2.31.0` package (not assumed from docs)**: its own `embedContent`'s internal `tContentsForEmbed` transform maps a plain `string[]` passed as `contents` to one separate `Content` per string (confirmed by reading the compiled SDK source), and `EmbedContentResponse.embeddings` is documented as "in the same order as provided in the batch request." This matters because an earlier, different SDK (`@google/generative-ai`) had a batching gotcha where a plain string array could get merged into one multipart content — that risk does **not** apply to this SDK's `embedContent`, so no extra wrapping (`{parts:[{text}]}` per item) is needed. The one-content-at-a-time restriction that does exist in the SDK's source only applies to the Vertex AI path for certain models, never to the Gemini Developer API (AI Studio key) path this project uses.

**Normalization**: `gemini-embedding-001`'s native output is 3072 dimensions, pre-normalized by Google. Truncating to a smaller `outputDimensionality` (768 here, chosen to fit Atlas M0's 512MB cap) is **not** auto-normalized by the API — confirmed via `ai.google.dev`'s own embeddings guide, which explicitly says non-3072-dimension output must be normalized manually. `GeminiLlmProvider` L2-normalizes every vector itself before returning it, regardless of dimension, rather than trusting the API's output to already have unit norm.

**Design choice — result types, not exceptions**: `embed()` returns `{ok:true,...} | {ok:false,error:{code,message}}` rather than throwing, matching the tool runner's Milestone 1 pattern. A missing API key, a rate limit, or bad input are routine, expected outcomes for an embedding call, not exceptional ones — RULES.md's "return typed errors from services" applies the same way here as it did to connector tool calls.

**Free-tier data-usage finding**: on the Gemini API free tier, Google's terms treat it as an "Unpaid Service" and explicitly reserve the right to use submitted content and generated responses to improve Google's products; human reviewers may read/annotate it. The paid tier's terms state the opposite. Documented directly in `.env.example` next to `GEMINI_API_KEY`: do not send real company policy documents or customer data through the free tier.

**Interview Q&A**: *"How did you avoid the classic batching gotcha where a model merges multiple texts into one embedding?"* — By reading the actual installed SDK's compiled source rather than trusting a summary of the docs: `@google/genai`'s `embedContent` maps each array element to its own separate `Content` before sending the request, and its response type is documented as one embedding per input, in order. That's also proven with a unit test against a fake client shaped exactly like the real request/response contract, not just asserted from the docs.

## Milestone 2, Stage 2 follow-ups — bounded limiter, trust proxy, explicit index ownership

**Failed-attempt limiter was unbounded in practice**: `FailedAttemptLimiter`'s `windowMs` expiry only reclaims an entry the next time *that same key* is looked up — a key queried exactly once (e.g. one failed attempt from each of many distinct source IPs) stayed in the Map forever. Fixed with a `maxEntries` cap (default 5000) and oldest-first eviction on overflow, using the Map's own insertion order rather than adding a second data structure.

**Trust proxy**: `req.ip` (what the limiter keys on) resolves to whichever peer connects directly to the Node process — if that peer is a reverse proxy (as Render's free web service is), every client collapses into one shared key. Added `app.set('trust proxy', 1)` in `main.ts`, trusting exactly one hop, matching Render's single-proxy topology; local Docker Compose has no proxy at all, so the setting is harmless there too (there's no X-Forwarded-For to trust, so `req.ip` falls back to the direct socket address regardless).

**Mongoose `autoIndex` made explicit**: was relying on Mongoose's own default (`true`) rather than stating it. Decision: `autoIndex: false` everywhere, with `db:ensure-indexes` extended to also call `Model.syncIndexes()` for every schema's regular (non-Atlas-Search) indexes — e.g. the unique index on `ApiKey.hash`. This keeps exactly one script, run manually, owning *all* index creation (both ordinary MongoDB indexes and the Atlas Vector Search index), rather than two different mental models for the two kinds of index.

## Milestone 2 — Database decision: MongoDB Atlas (M0) with Atlas Vector Search, via Mongoose

**Decision**: MongoDB Atlas, free M0 cluster, using Atlas Vector Search for policy chunk retrieval, accessed through Mongoose.

**Why, over Postgres + pgvector**:
- **One system for both data and vectors.** `PolicyChunk` documents and their embeddings live in the same collection, queried with one `$vectorSearch` aggregation stage rather than a separate vector extension bolted onto a relational table. For a document-shaped domain (tenants, documents, chunks, conversations, agent steps — all naturally nested/variable-shape records), this fits better than forcing a relational schema.
- **Tenant isolation is structurally simple.** `tenantId` is just another field on every document, pre-filtered inside the same `$vectorSearch` call via the index's `filter`-type fields (see the Milestone 2 plan for the exact mechanism) — no separate row-level-security configuration needed, as Postgres would require for the same guarantee.
- **Free tier genuinely supports it.** Verified directly against current MongoDB docs (not memory): Atlas free (M0) clusters support up to 3 Search/Vector Search indexes combined, with 512 MB storage. That's enough for this project's one tenant-filtered vector index plus headroom.

**Trade-offs accepted, against Postgres + pgvector**:
- **512 MB storage cap** is smaller than Neon's free tier — chunk text must stay lean (store extracted text only, not raw uploaded files, per RULES.md section 7).
- **3-index ceiling** means the vector index design must be deliberate from the start — one shared index with a `tenantId` filter field, not one index per tenant (already the documented design in `PROJECT.md` section 3).
- **No SQL joins or relational integrity** — trade-offs are handled at the application layer (Mongoose schemas + repository interfaces) rather than database constraints. Acceptable here since the data model (per `PROJECT.md` section 5) has few true relational constraints — mostly parent-child references (chunk → document → tenant), which Mongoose's `ref`/`populate` or manual `tenantId` scoping covers adequately.
- **Index creation is asynchronous** (not instant on write) — the app must poll `listSearchIndexes()` for `queryable: true` before relying on a newly created index, which Postgres's synchronous `CREATE INDEX` wouldn't require. Handled once in a small startup/bootstrap routine, not a recurring concern.

**Interview Q&A**: *"Why MongoDB over Postgres for a RAG system, when pgvector is also free and well-known?"* — Because the actual data (multi-tenant documents, chunks, conversation traces, agent steps) is naturally document-shaped, not relational, and Atlas Vector Search keeps the embeddings in the same collection as the data they describe instead of a bolted-on extension. The real constraint that shaped the design was the free tier's 3-index cap, which is why the project uses one shared vector index with a `tenantId` filter field rather than per-tenant indexes — same discipline pgvector would need under a hosted free tier's own index-count limits.

## Milestone 0 — TypeScript pinned to 6.0.3, not 7.x

**What**: the root and `apps/api` `package.json` pin `typescript` to `6.0.3` instead of the registry's `latest` tag (`7.0.2`).

**Why**: TypeScript 7 is Microsoft's native Go-ported compiler. Its `7.0` release supports `experimentalDecorators` and `emitDecoratorMetadata` (the design-time metadata NestJS's dependency injection reads at boot), but it ships no compiler API yet — that returns in `7.1`. `@nestjs/cli`'s `nest build` command depends on that API, so it cannot build a Nest app under TypeScript 7.0 today.

**Trade-off rejected**: staying on `7.0.2` and building with plain `tsc` instead of `nest build`, bypassing the Nest CLI. Rejected because it would mean hand-rolling what `nest build` already does (asset copying, webpack/SWC build modes) for no real benefit this early, and it diverges from the standard NestJS workflow interviewers would recognize.

**Revisit when**: TypeScript 7.1 (or later) restores the compiler API and `@nestjs/cli` confirms support for it. Check the registry and `@nestjs/cli`'s release notes before upgrading.

**Interview Q&A**: *"Why is this project on an older TypeScript line when a newer major is out?"* — Because the newer major (TypeScript 7, the Go-native compiler) dropped its compiler API in its first release, which the NestJS CLI's build command depends on. Pinning to the last compiler-API-complete release (6.0.3) keeps the standard Nest build pipeline working; the dependency is tracked for an upgrade once 7.1 restores that API.

## Milestone 0 — tsconfig used deprecated moduleResolution and baseUrl

**What went wrong**: `tsconfig.base.json` set `"module": "commonjs"` with `"moduleResolution": "node"` (which TypeScript resolves to the `node10` strategy), and `apps/api/tsconfig.json` set `"baseUrl": "./"`. TypeScript 6.0.3 treats both as hard errors (`TS5107`, `TS5101`) because they're slated for removal in TypeScript 7.0, so `nest build` failed before any of our code even compiled.

**The fix**: changed `module` and `moduleResolution` to `"nodenext"` together (they must match — `commonjs` paired with a `node16`/`nodenext` resolution strategy is invalid) and removed `baseUrl` entirely, since nothing in the codebase uses path aliases. `apps/api/package.json` has no `"type": "module"`, so under `nodenext` the compiler still emits CommonJS output and relative imports still don't need `.js` extensions — only packages that opt into ESM via `"type": "module"` get the extension requirement.

**Why not just silence it**: TypeScript offers `"ignoreDeprecations": "6.0"` to suppress these specific errors, but that only delays the same break to TypeScript 7.0 rather than fixing it — the deprecated options still wouldn't work there. Fixing the actual settings now means the config is already 7.0-ready whenever the compiler-API gap (see the TypeScript 6.0.3 pin entry above) is resolved.

## Milestone 0 — nest build emitted dist/src/main.js instead of dist/main.js

**What went wrong**: `apps/api/tsconfig.json`'s `include` listed both `src/**/*.ts` and `test/**/*.ts` with no `rootDir` set. TypeScript infers `rootDir` as the nearest common ancestor of every included file when it isn't given explicitly — here, that's `apps/api/` itself, since `src/` and `test/` are siblings. So the compiler mirrored that structure under `outDir`, producing `dist/src/main.js` and `dist/test/*.spec.js` instead of a flat `dist/main.js`. The `start` script (`node dist/main.js`) and the Dockerfile `CMD` assumed the flat layout and failed with `MODULE_NOT_FOUND`.

**The fix**: a separate `apps/api/tsconfig.build.json` that extends the main `tsconfig.json`, sets `rootDir: "./src"`, and narrows `include` to `src/**/*.ts` only (excluding `test/`, `**/*.spec.ts`, `dist`, `node_modules`). `nest-cli.json` points `compilerOptions.tsConfigPath` at this build config. The original `tsconfig.json` is untouched and still covers `src/` + `test/` together, so the editor, ESLint, and Vitest keep type-checking both.

**Why a separate build tsconfig, not one tsconfig doing both jobs**: type-checking and editor tooling want the widest `include` (so tests get type errors too), but compilation output wants the narrowest `include` (only what ships to `dist/`, with `rootDir` pinned so the output path is predictable). One tsconfig can't satisfy both without compromising one side — this split is the standard Nest CLI pattern (`nest new` scaffolds projects this way by default) for exactly this reason.

## Milestone 1 — node:http with a custom `lookup`, not fetch, for the tool runner

**What**: the tool runner sends every outbound connector request via `node:http`/`node:https`'s `request()`, never the built-in `fetch`, with `agent: false` (a fresh, non-pooled connection per call) and a custom `lookup` option.

**Why**: this closes a real DNS-rebinding gap that a fetch-only pre-check can't. `fetch` resolves DNS internally, with no hook to re-validate the address at the moment it actually connects — so a hostname could pass an earlier SSRF check and then resolve to a private IP by the time `fetch` itself connects, moments later. `http.request`'s `lookup` option runs at that exact connect moment, so validation and connection happen atomically. `agent: false` additionally guarantees a prior validated connection is never silently reused for a different, unvalidated target.

**What I found by testing it, not assuming it**: Node only invokes the custom `lookup` function when the target is a *hostname* — for a literal IP target, Node skips DNS resolution (and `lookup`) entirely, which is correct and safe (there's no resolution step to rebind in the first place). My first test for "lookup runs on every request" used a literal IP as the stub server's URL and silently proved nothing — `resolveDns` was called zero times, not because the feature was broken, but because the test never actually exercised the lookup path. Fixed by pointing the test at a hostname instead. Also confirmed directly: Node calls `lookup` with `{ all: true }` by default, which is why the lookup function has to handle both the single-address and array callback shapes, not just one.

## Milestone 1 — ToolRunnerSettings must boot with an empty host allowlist

**What went wrong**: `ToolRunnerSettingsSchema` originally required `hostAllowlist` to have at least one entry (`.min(1)`). Starting the built app with `NODE_ENV=production` and no tool-runner env vars set at all crashed at Nest's bootstrap, because `CONNECTOR_HOST_ALLOWLIST` defaults to an empty list and the schema rejected it.

**The fix**: removed the `.min(1)` constraint. An empty allowlist is a valid, safe configuration — it just means no connector is currently permitted to make outbound requests, which is the correct conservative default for an unconfigured deployment, not an error condition.

**Why this matters beyond the one bug**: it's a concrete instance of "fail fast on genuinely invalid config, but don't treat the safest possible default as invalid" — a container that won't start because nothing has been configured yet is worse than one that starts and simply permits nothing until an operator sets the allowlist.

## Milestone 1 — a size-limit test that didn't test the size limit

**What went wrong**: the first version of the "oversized response" test set `Content-Length: 5` and then wrote 2000 bytes, expecting the tool runner's own streaming byte-counter to catch it. It didn't — Node's own HTTP parser rejects a response that delivers more bytes than its declared `Content-Length` as a protocol violation, surfacing as a generic network error *before* our byte-counting logic ever got a chance to run. The test still "passed" in the sense that *some* failure occurred, but not the one it claimed to be testing.

**The fix**: rewrote the test to send a response with *no* `Content-Length` at all (chunked encoding), which Node cannot pre-validate the size of — that's the actual scenario our own streaming counter exists to defend against, and it's the one real "lying" servers can get away with (declaring too little is caught by Node itself; declaring nothing at all is not).
